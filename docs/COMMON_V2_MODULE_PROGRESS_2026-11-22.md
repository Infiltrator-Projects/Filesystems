# Current Common V2 filesystem work — 22 November 2026

## Qualification boundaries

The canonical interface is [Libraries Common V2](https://github.com/Infiltrator-Projects/Libraries/blob/main/include/infiltratr/filesystem_module_v2.h). Every source-tree provider currently exposes `infiltrator_filesystem_api_v2`. This document records **current source capabilities**, actual latest **GitHub release versions**, and observable tests. It does not equate compilation with a successful boot.

**BOOT is being migrated separately and was not modified.** Its final authenticated Common V2 loader and OVMF kernel/initramfs handoff have not been exercised against these released modules, so no boot-capable provider is yet marked end-to-end accepted. Firmware “namespace” means the source advertises and tests the genuine V2 PROBE/MOUNT/STAT/LIST/READ callbacks on supported on-disk features; `SWAP` must not implement a fake namespace. Historical machine-specific validator observations are intentionally excluded.

## Changes committed and released in this qualification cycle

EXT4's canonical-core unit test was repaired without leaking V1/private symbols ([commit](https://github.com/Infiltrator-Projects/Filesystem-EXT4/commit/7310afae5284365ebc7fd2e3df596e43ddaffb33)); release v1.0.19 and both build/release workflows passed. Newly qualified, published `.deb` and native `.run` assets are also available for APFS v1.0.13, Btrfs v1.0.12, exFAT v0.1.17, EXT2 v1.0.16, EXT3 v1.0.15, HFS v1.0.13, HFSPlus v1.0.12, Minix v1.0.16, PFS3 v1.0.12, SFS v1.0.11, SFS2 v0.1.8, Swap v1.0.12, UFS1 v1.0.13, UFS2 v1.0.20, and XFS v1.0.14. The new releases omit old `.ko` assets.

NTFS's current main source includes a real bounded freestanding Common V2 MFT, INDEX_ROOT/INDEX_ALLOCATION and data-stream reader in `native/ntfs_ro_v2.c` linked into the packaged firmware ELF. Real 512/4096-byte geometry, kernel and initramfs reads, MFT fixup and dirty-volume corruption checks run through the actual extracted package binary. [NTFS v1.0.20](https://github.com/Infiltrator-Projects/Filesystem-NTFS/releases/tag/v1.0.20) **was published after both build and release workflows passed using a real Linux kernel and a distinct generated initramfs**, with a .deb, native .run and SHA256SUMS manifest. The 22 November 1.0.21 source tree now compiles **the same `native/ntfs_ro_v2.c` reader into both hosted and freestanding profiles**. Hosted CORE.STAT/LIST/READ and DEFRAG.MAP call that native reader; the old NTFS-3G pathname/extent mapper has been deleted. The 1.0.20 tag does **not** include those changes, and main 1.0.21 package qualification remains pending. See [NTFS V2 status](https://github.com/Infiltrator-Projects/Filesystem-NTFS/blob/main/docs/COMMON_V2_BOOT_STATUS.md).

Defragmenter current main has now **removed all production V1 filesystem ABI interfaces** from its workers, host dispatch and Test Media. A strict dispatcher refuses every export other than `infiltrator_filesystem_api_v2` before a module or target opens; the 15 native worker routes and native Test Media now request only Common V2 capability groups. Retired V1 headers, host services, source adapters and legacy integration workflows were removed. Direct current-main source inspection of all 75 production native/Test Media/core C and C++ files found no retired V1/V3/V5 filesystem interface references. The dedicated negative test intentionally **contains** obsolete symbol names to verify that fake V1/V5-only providers are not discovered or executed; these are test fixtures, not production support. The independent 23-filesystem V2 acceptance matrix and complete native quality gate have been committed but **their latest GitHub Actions results are still queued/pending**, so no new release or complete CI pass is claimed. Formats lacking real Common V2 DEFRAG PLAN/EXECUTE/VERIFY/RECOVER capabilities now fail closed rather than invoking a private or previous ABI. The full production Common V2 VOLUME/DEFRAG feature migration remains the responsibility of each filesystem provider.


## Release rule

Do not mark a module fully BOOT-qualified until its exact published `.so` has passed the unmodified future production Common V2 BOOT validator and real OVMF read-only mounting, directory listing, kernel/initramfs reads, corrupt-feature refusal and unchanged-image qualification. No user's machines or BOOT Git repository code were changed.
